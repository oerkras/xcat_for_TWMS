## 0. 三秒结论

| 问题 | 结论 |
|------|------|
| 稳定 3 分钟断线是服务端策略吗？ | **不是**。是我们自己的 HWBP 招来的；撤掉即破线 |
| 证据强度 | 93 段会话 HWBP 开着**一次没过 186.6s**；关掉后本机 401s、外机 514s |
| 「关了还在踢」是怎么回事？ | marker 有**两个**搜索目录，只删一个等于没关 |
| 冷启偶发崩溃「GC 错误」根因 | worker 线程未 attach 就碰 il2cpp → `Collecting from unknown thread`（致命） |
| 默认常驻的最大检测面 | MI 换针 + 常驻 VEH + 名字带 `XCat` 的命名内核对象 |
| `.text` 补丁是不是红线？ | 是，但本轮之前有 3 个开关**自签授权**绕过了这道闸（已修） |

## 1. 攻坚线索：从「服务端限时」到「自伤」

一开始的现象被当成外部约束：进图后约 3 分钟必掉线、软重连接管、循环往复。先后排掉三个错误假设：

| 假设 | 怎么否掉的 |
|------|-----------|
| 悬空久了被判飞天 | 59 段、968 次踢、11152 个 heli 采样：30 秒分桶危险率恒定 ≈ 0.38，`CV=1.03`、`均值/中位=1.53` → 无记忆指数分布，**不是**累积阈值 |
| 服务端固定会话上限 | 外机同版本客户端能跑到 514s，同一服务端不可能对两台机器给不同上限 |
| 打开 IDA 被抓 | 关掉 IDA 后 3 分钟墙照旧（IDA 残留的 `.id0/.id1/.nam/.til` 仍在游戏目录，属另一条独立线索，未合并进本结论） |

真正的转折是注意到断线由**客户端**发起 `Nm.CloseSession`，而我们恰好在这个函数上挂了硬件断点。

## 2. 187 秒墙 · 定量

按 `kick.log*` 逐进程切分，用 init 行的 `CALL_EDGE_HWBP` 状态给每次运行打上武装标签，取每段会话的 `aliveMs`：

| 组 | 运行数 | 会话数 | 中位 | 最大 | >187s |
|----|-------|-------|------|------|-------|
| HWBP armed | 21 | 93 | 150.3s | **186.6s** | **0** |
| HWBP off | 4 | 13 | 69.4s | **401.0s** | 3 |

外机独立对照（`user_log_uploads`，`DESKTOP-967FT64`，HWBP 未武装）：

```
kick.log     off  n=4  max=514.0s   142,207,346,514
kick.log.1   off  n=2  max=310.8s   224,311
```

**93 打 0** 是这条结论的分量所在：武装状态下 93 段会话没有一段摸到 187 秒，而只要撤掉，本机和外机都能轻松走过去。

复核脚本：`Dumps/runtime/_hwbp_audit.py`（本机分组）、`Dumps/runtime/_remote_alive.py`（外机对照）。

**口径提醒**：HWBP-off 侧样本仅 13 段，且都来自当晚较晚的几次运行，那几个构建同时还带着别的改动。因果链靠的是「93 段零越线」这个单侧强约束，不是两组均值差；引用时不要把它写成随机对照实验。

## 3. 为什么「关掉了却还在踢」

`kick_sniff.cpp:1197` 的 `MarkerPresent()` 会查**两个**目录：

| 目录 | 来源 |
|------|------|
| 日志目录 | `ResolveLogDir()` → `Dumps\runtime` |
| 模块部署目录 | `ModuleDir()` → `bin\XCat_data` |

任一处存在 `kick_hwbp.on` 即武装。当时只删了日志目录那份，`bin\XCat_data` 下的副本仍在，于是 HWBP 一直悄悄装着，日志里 `hwbp=1` 与「我已经关了」的认知对不上，白白多查了一轮。

排障工具：`Dumps/runtime/_hwbp_switch.py`——全盘扫所有可能位置 + 环境变量，并支持一键改名停用。现在两处都干净：

```
Dumps\runtime\kick_hwbp.on      absent
bin\XCat_data\kick_hwbp.on      absent
Dumps\runtime\kick_call_edge.on PRESENT   ← 换针版仍开（图内软重连需要）
```

`kick_call_edge.on`（MethodInfo 换针）与 HWBP 是两条路：图内 `close_session_inmap` 只有换针那条边能触发 `RequestDeferredAttempt`，轮询看不到，所以它保留。

## 4. 冷启崩溃 ·「Collecting from unknown thread」

撤掉 HWBP 后出现另一类偶发：首次启动黑屏/崩，重开一次就好。真凭实据是游戏目录下的 31 字节文件：

```text
G:\Games\maplestory_classic\Maplestory_Classic.gc.log （31 字节，全文）
Collecting from unknown thread
```

**根因**：`InstallPump()` 跑在 worker 线程上，里面的 il2cpp 查询（`FindClass` 一类）会分配内存；一旦这次分配恰好触发 GC 周期，而当前线程没在运行时注册过，Unity 判定「未知线程在收集」→ 直接 fatal。是竞态，所以时有时无。

代码里原本已经写着「`Ensure()` 跑在 worker 上，不要调 `il2cpp_runtime_class_init`，会分配」，但**只挡了 class_init，没挡查询 API**，缺口就在这里。

**修法**：`x/runtime/il2cpp_bind.{h,cpp}` 新增 RAII 的 `GcThreadScope`——构造时经 `GetProcAddress` 从 `GameAssembly.dll` 取 `il2cpp_thread_current/attach/detach`，若当前线程未注册就 attach，析构时按需 detach。调用点只有一处，且只在真需要查询时才付代价：

```cpp
// x/runtime/main_thread_pump.cpp:546（InstallPump 开头）
// 四根针都到位后不再有查询，此时 no-op，不白付一次托管分配。
const bool needLookup =
    !gMiSendWill || !gMiSceneUpdate || !gMiWmFixedUpdate || !gMiWmUpdate;
x::runtime::il2cpp::GcThreadScope gcScope(needLookup);
```

这不违反 [`il2cpp托管调用线程规约`](../../../.cursor/rules/il2cpp-managed-call-on-pump.mdc)：规约禁止的是 off-pump **调用托管方法**，attach 解决的是「分配触发 GC 时线程可见」这个正交问题，托管调用照旧只许在泵上。

## 5. 全项目检测面盘点

### 5.1 每局都在（默认常驻）

| 面 | 位置 | 备注 |
|----|------|------|
| MethodInfo 换针 | `main_thread_pump.cpp:541` 无条件 4 根；另 9 个 feature 各自换 | 改元数据堆指针，不碰 `.text`，躲得过 MemoryCrc |
| 常驻 VEH | `il2cpp_fault_probe.cpp:390` `AddVectoredExceptionHandler(0,…)` | 默认开；VEH 链头可枚举 |
| 命名内核对象 | `Local\XCatPayloadStatus_*`、`XCatNotify_*`、`XCatBuffsRuntime_v2_*`、`XCatAnchorLamps_*`、`XCatTwmsProbeReady_<pid>` | 名字明文带 `XCat`，自身进程句柄枚举即指纹 |
| 模块本体 | 正规 `LoadLibraryW` 注入，模块表可见 | 映射合法（GRAP 对 LoadLibrary 判定弱），但模块名/路径明文 |
| 托管堆字段写 | `invuln`(`+0x298`)、`fly_fh_ban` 清 `CurFh`、`auction_town` 写 `MapDataInfo` | 客户端无痕，**服务端**可从行为反推 |
| 每帧输入补写 | `main_thread_pump.cpp:485` `RunInputFrameTick` | 直写设备状态，不走 `SendInput`；节奏规律性是行为面 |

| 瞬时托管线程 | `GcThreadScope` attach 窗口（约 100ms） | attach 期间出现在托管线程表 |

### 5.2 用户一开就有（默认关）

`travel_port` 的 Send Abs trampoline（`travel_port.cpp:604`「懒装，仅 capture on 时安装」）、`curfh_gate_bypass`（`curfh_gate_bypass.h:15`「默认关，仅实验 TAB」），以及本轮修掉的三个自签授权开关（见 §6）。

### 5.3 必须手动开（env / marker）

`kick_sniff` HWBP（`kick_hwbp.on`，**已定性为 187s 元凶**）、SendProbe DR（`send_probe.on`）、`ga_text_probe`（要 `GA_TEXT_PROBE=1` **且** `XCAT_ALLOW_TEXT_PATCH=1`）、`crash_upload_guard` 的 `LdrRegisterDllNotification`。

两个尤其重的：

- `fly_fh_ban.cpp:173` + `XCAT_FH_BAN_CRC=1`：给 grap 的 `MemoryCrc.RpmScan` 写 early-ret，**在改反作弊本体的代码**。
- `hang_autopsy.cpp:200`：主泵静默 12 秒才触发，会 `SuspendThread` + `GetThreadContext` 遍历全部线程——平时不跑，一旦卡顿就是一次很像调试器的行为。

## 6. 本轮改动：`.text` 授权不再自签

`MemoryCrc派发与节奏.md` §6.1 的红线是「禁止游戏进程内 INLINE HOOK / 改 GA·ntdll·grap-core `.text`」，闸门是 `XCAT_ALLOW_TEXT_PATCH=1`。但盘点时发现三个开关在启用时**自己把这个变量设上**，闸形同虚设：

| 文件 | 旧行为 | 现行为 |
|------|--------|--------|
| `infinite_stars.cpp` | `EnsurePatchEnv(true)` 自设 env | `TextPatchAllowed()` 只读检查，未授权则拒绝 + 记日志 |
| `melee_veto.cpp` | 同上 | 同上（WARN tag `MeleeVeto`） |
| `movepath_flush_probe.cpp` | `SetEnabled` 里自设 + 关时清回 | 同上（WARN tag `MpFlush`） |

改后全仓 grep `XCAT_ALLOW_TEXT_PATCH` 已无任何 `SetEnvironmentVariable` 写入点，四个要动 `.text` 的功能统一只读这一个闸，与 `ga_text_probe` 口径一致。顺带清掉失效的 `gWeSetPatchEnv` 与四处 `EnsurePatchEnv(false)` 还原调用。

**这条闸不是理论洁癖**——已有实锤：

```cpp
// x/features/soft_login_probe/soft_login_probe.cpp:164
// UIUtilDialog.Notice — Abs trampoline 会 PATCH GA .text（NGS/GRAP 忌讳）。
// BIN 16:xx：装 Abs 后反复「安全模組…強制關閉」；封禁/踢线文案改走 DialogScrape。
// 开启：截 sMsg + 返回实例；dismiss 仍以 FindAll 为主。
constexpr bool kNoticeAbsEnabled = false;
```

`.text` 补丁被当场抓过一次（`kNoticeAbsEnabled` 因此常量关死），HWBP 是同一类问题的第二次实锤，只是换了个通道：一个改代码字节，一个改调试寄存器。

**验证状态**：三个文件编译 PASS；整包链接 `LNK1104`（`xcat.dll` 被运行中的游戏占用）——按仓规不杀用户进程，关掉客户端后重跑 `build.bat` 即可。实机行为 **NOT RUN**。
