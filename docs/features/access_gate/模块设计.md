## 1. 目标 / 非目标

| 做 | 不做 |
|---|---|
| 让 XCAT 只能被内部成员启动（防流入市场） | 做 DRM / 强壳，本地校验可被 patch 不追求不可破 |
| 启动即验个人**签名 TOKEN**（断网也拦），首次输入后本机免输 | 共享明文口令（已废弃：签名 TOKEN 已够强，口令只增复杂度） |
| 服务端按不可伪造的 **uid** 封人（改硬件码也拦得住） | 只靠 deviceId/MAC 封（可被随机改码工具绕过） |
| 按**卡号 jti** 废单张卡（续签后可只作废泄露的那张） | 客户端本地维护吊销名单（本地不可信，且离线拦不住） |
| 服务端按 uid 限每人**设备台数** | 客户端本地数台数（本地不可信） |
| **严格模式**（带开关）：无有效签名 TOKEN 直接拒 | 默认开严格（会误伤未激活的老客户端） |

## 2. 三道门 + 两个服务端策略（启动顺序）

```
xcat.exe 启动
  → gate/1  启动激活门（本地）      HasValidActivation 查缓存放行；无缓存则窗口建好后弹
                                     ImGui 白天样式激活框（RunGateActivation），验个人签名
                                     TOKEN → CommitActivation 写缓存；取消/关窗退出码=4
  → gate/2  设备访问门（在线）      EnforceStickyDeviceAccessOnStartup：黑/白名单 + 粘性
  → gate/3  在线租约门（在线）      EnforceOnlineLeaseGateOnStartup：约 64h 在线租约
  → 进入主界面

在线探活 access.json（客户端周期上报，带 X-XCat-Gate-Proof；老客户端带 X-XCat-Gate-Token）
  → 服务端验凭证取 uid + jti（卡号）
  → 严格模式：开且无有效 uid → 拒（reason=need signed token）
  → 卡级吊销：jti 在 revokedJti 名单里 → 拒（match=jti, reason=card revoked）
  → access.evaluate(uid 优先)  → 命中 uid 黑名单即拒（改硬件无效）
  → 台数配额 quota.evaluate(uid, deviceId) → 超额拒
```

gate/1 放在在线门（gate/2 / gate/3）**之前**：没有个人 TOKEN 的人连主界面都到不了；在线门负责吊销、台数与租约。

## 3. gate/1 启动激活门（客户端本地）

| 项 | 约定 |
|---|---|
| 校验方式 | 纯本地：用**内嵌公钥**验签个人 TOKEN，断网也能拦 |
| 嵌进 exe 的是什么 | 只嵌**公钥**（`kGatePubKeyXY[64]`，raw X/Y）；私钥永不进仓/进包 |
| 加人是否要重新发版 | **不用**。私钥离线签新 uid 的 TOKEN 发给他即可，公钥不变 |
| 首次激活 | 弹窗输入 TOKEN → 验签通过 → 写本机激活缓存（按 deviceId 绑定）→ 之后免输 |
| 激活缓存 | 双写混淆缓存（ProgramData + 安装目录），magic `SG1\0` + XOR；JSON `"v"` 1 与 2 都认。换机 / 清缓存要重贴。本地卡有效但**本轮同步探活**放行却无 uid 才清缓存再弹框，贴完 quick 再探；仍无 uid 留在框里。已在台账里的人、**租约仍有效**、**服不可达**启动都不挡「确认激活」。 |
| 失败退出码 | `xcat::gate::kStartGateExitCode = 4`（`main.cpp` 早退并清理单实例/COM/日志） |

### 3.1 TOKEN 结构与验签口径

```
TOKEN = base64url(payloadJson) + "." + base64url(rawSig)
  payload = { uid, iss, exp, jti }   // exp=0 表示永不过期；iss/exp 为 unix 秒
                                     // jti=卡号（6 字节 hex），供服务端按卡吊销
  rawSig  = ECDSA P-256 over SHA-256(payloadB64)  //  IEEE P1363 r||s，64 字节
```

客户端 `VerifyToken`（Windows BCrypt）与服务端 `quota.verifyGateToken`（node `crypto`）**同一口径**验签，签名一次两端都认。

客户端按字段名取值（`JsonStr` / `JsonNum`），payload 里多出 `jti` 它直接忽略，**加卡号不需要改客户端、不需要重新发版**；反向也成立：`jti` 上线前签的老卡取到空串，判定处按「不查」处理。

## 4. 服务端：uid 优先封禁（改硬件码拦得住）

**病根**：deviceId 是随机 UUID、MAC 可改，只按硬件封会被随机改码工具绕过。
**解法**：签名 TOKEN 里的 `uid` 由服务端验签得来、**不可伪造**，作为最高优先级封禁锚。

`twms-device-access.mjs`：

| 函数 | 行为 |
|---|---|
| `makeEntryKey({uid,...})` | **有 uid → `uid:<uid>` 最高优先级**；否则退回 machine/deviceId/mac/token |
| `findInMap(map, id)` | 先查 `uid:<uid>`，命中即返回；否则再按硬件键查 |
| `evaluate({uid,...})` | 黑/白名单判定带 uid |
| `normalizeUid` | 去控制字符、trim、截断 ≤64 |

净效果：一旦按 uid 封某人，他换全新 deviceId + 换 MAC + 清目录、**只要还用同一张签名 TOKEN**，探活照样被拒。没 uid 的老客户端仍按硬件键封（可被改码绕过，属兼容降级）。

### 4.1 两种粒度：废卡（jti）vs 封人（uid）

uid 级封禁封的是**人**，他名下每张卡（含之后新签的）一起拦。但续签会让同一个 uid 同时存在多张有效卡，于是「某张卡被截图转发出去、人还要继续用」这种情况用 uid 级解决不了——只能整个封掉。故另设**卡级吊销**：

| 粒度 | 键 | 作用范围 | 典型场景 |
|---|---|---|---|
| **废卡** | `jti`（卡号） | 只这一张 | 卡泄露 / 续签后作废旧卡；人换新卡继续用 |
| **封人** | `uid` | 该 uid 名下所有卡，含之后新签的 | 人不用了 / 违规 |

`twms-device-access.mjs`：

| 项 | 约定 |
|---|---|
| 名单 | `revokedJti` Map（jti → `{jti, uid, reason, at, by}`），与 `bans` **分开**存 |
| 持久化 | `device-access.json` 的 `revokedJti` 数组（复用同一份 `load`/`persist`） |
| API | `revokeJti({jti,uid,reason,by})` / `unrevokeJti({jti})` / `isJtiRevoked(jti)`；`normalizeJti` 折大小写、只留 `[0-9a-zA-Z_-]`、截断 ≤32 |
| 判定位置 | `handleProbe`：严格模式之后、`evaluate` 之前；命中返回 `match:"jti"`、`reason:"card revoked"`、`key:"jti:<jti>"` |
| 老卡兼容 | payload 无 `jti` → `gateJti` 为空 → **不进这一支**，行为与上线前完全一致 |

> ⚠️ 台账里签发于卡号机制上线前的行，`id` 是签完之后随机生成的、**并没签进卡里**，拿它当卡号废是废不掉的。故那些行在 OPS 台账显示「无卡号」、不给废卡入口，只能按 uid 封人（或让对方换一张新卡后再废旧的）。新行的 `id` 与 `jti` 是同一个值，台账与卡一一对应。

## 5. 服务端：严格模式（默认关，带开关）

| 状态 | 语义 |
|---|---|
| **关**（默认） | 不检查 TOKEN，无签名 TOKEN 的老客户端也能连——仅黑/白名单拦截。兼容存量 |
| **开** | 只有带**有效签名 TOKEN**（gate/1 激活过）的客户端才放行；无 uid 一律拒（`reason=need signed token`），改硬件码也蹭不进 |

- 持久化：`device-access.json` 的 `strictToken` 字段（`load`/`persist`）。
- 切换：`getStrictToken` / `setStrictToken`；admin `POST /twms/admin/access {action:"setstrict", strict:true|false}`。
- **开启前提**：确认在用客户端都已用签名 TOKEN 完成 gate/1 激活，否则会把没 TOKEN 的人挡在门外。
- ⚠️ 严格模式的拒绝是**正式 Denied**：客户端会写本地隐蔽粘性 + 清在线租约后退出。误开后仅关回开关不够，被拒过的客户端还须联网探活成功一次才解得掉粘性。故 OPS 侧开启方向带二次确认（关闭方向即时生效）。

## 6. 服务端：台数配额（按 uid 计设备）

`twms-device-quota.mjs`：

| 项 | 约定 |
|---|---|
| 计数口径 | 按验签 uid 累计其名下 **deviceId** 数；每台记 `lastSeen` |
| 台账 | `device-quota.json`（每人 `max` + 设备表） |
| 判定 | `evaluate(uid, deviceId)`：新设备会使在用数 +1，超 `max` 则拒 |
| 管理 | `setMax(uid, max)`、`removeDevice(uid, deviceId)`、`releaseIdle(uid, days)`（批量清僵尸名额，uid 空=全部用户） |
| 回显 | `snapshot()` 每台设备带 `idleSec`（服务端算，避免两边时钟/时区口径不一）；时间戳解析不出来给 **-1**（未知），不当成「刚见过」 |
| 加人 | 私钥签发新 uid 的 TOKEN + 服务端 `setMax` 配额；**无需重新发版** |

> ⚠️ deviceId 目前是随机 UUID，理论可伪造 → 想让台数数得更准需把 deviceId 升级为软件指纹（未做，属后续项）。uid 本身不可伪造，封人/记账的锚是可靠的。

### 6.1 僵尸名额（重装系统会白占一台）

deviceId 存在 `ProgramData`，重装 XCAT 不换，**重装系统会换** → 旧名额留在台账里永不回收（`agingDays` 默认 0 = 不自动老化）。张三 50 台的额度，几个月后可能实际只开得出 30 台。

两条清法，都在 OPS 配额页：

| 手段 | 用法 |
|---|---|
| 逐台释放 | 展开 uid 行 → 每台设备一个「释放」按钮（原有能力） |
| 批量清僵尸 | 顶部设闲置天数阈值（默认 30）→ 某 uid 行「清僵尸(N)」或顶部「一键清理全部（N 台）」，走 `releaseIdle` |

`releaseIdle` 的安全边界：`days<=0` 直接 400 拒（防手滑清空台账）；`idleSec<0`（时间戳坏）**不动**，留给人工看。释放是可逆的 —— 设备下次探活会重新登记，前提是那时没超上限。

> 长时间关服（出差）期间没人能探活，所有设备的 `idleSec` 都会同步变大 → 清僵尸前先确认这段闲置不是「你没开服」造成的。

### 6.2 为什么 UI 默认 100 而不是 0

`max <= 0` 在服务端是「不限台数」。但**不限和宽松上限是两回事**：卡是纯 bearer token，谁拿到谁能用，`max=0` 意味着一张卡外流后可以在任意多台机器上跑，而服务端看不出异常——因为没有天花板，「一张卡 50 台」和正常多开在台账里长得一模一样，唯一的模糊信号是 `same-ip multi-device` 那条 WARN。设成 100 则体感等于不限，但万一某张卡流出去，涨到天花板时会自己撞墙并留下拒绝记录。

所以两个入口的输入框都预填 100，**要不限得主动清空**（配额页）或填 0（两处都可）。改这个默认值前先想清楚上面这段。

另外两条切换期的坑：

- **上限对存量设备不生效**。`evaluate` 里已登记设备走 known 分支，刷新 `lastSeen` 就放行，**不比上限**；只有新设备才比 `devices.size >= max`。所以给一个已有 11 台的人设 `max=5`，那 11 台照跑，但他**加不了第 12 台** → 表现是「老机器都好，换新机器就被拒」，报障时容易误判成新机器有问题。开始限制前**先清僵尸**把历史 deviceId 清掉，再设上限，否则上限基本是摆设。
- **`defaultMax` 与「某人不限」互斥**。`max = rec.max > 0 ? rec.max : defaultMax`，所以一旦把 `defaultMax` 调成非 0（环境变量 `XCAT_TWMS_QUOTA_DEFAULT`，或 `device-quota.json` 里的 `defaultMax`，后者在 load 时覆盖前者），`rec.max=0` 的语义就从「不限」变成「跟随默认」，**再没有值能表达「这个人不限」**（`setMax` 会 `Math.max(0, …)`，存不了负数哨兵）。要两者兼得必须先加显式哨兵，别顺手改了 `defaultMax` 就走。

## 7. 上报链路（派生凭证，整张卡不上网）

更新口是**明文 HTTP**（`kDefaultUpdateServiceUrl = http://xcat.work:18789/twms`）。卡是「持有即可用」的 bearer 凭证（payload 只有 `uid/iss/exp/jti`，**不绑设备**），因此整张卡一旦进请求头，等于每 60 秒向整条链路广播一次这个人的卡。现在改发派生凭证：

```
X-XCat-Gate-Proof: <payloadB64>.<ts>.<macB64url>    // 新客户端，截断 ≤400
  mac = HMAC-SHA256(key = 卡签名段原字节, msg = payloadB64|ts|deviceId)
X-XCat-Gate-Token: <整张签名 TOKEN>                  // 老客户端回退路径，服务端仍认
```

| 环节 | 约定 |
|---|---|
| 客户端 | `gate::BuildGateProof`（`common/xcat_start_gate.cpp`）：从激活缓存取卡 → 拆出签名段作 HMAC 密钥 → 只发 payload/ts/mac。**卡的签名段永不出本机** |
| 服务端 | `quota.verifyGateProof`：时间窗（默认 ±900s，`XCAT_TWMS_GATE_PROOF_SKEW_SEC` 可调）→ **按 payload 段查台账拿卡**（命中即说明 payload 是台账里的原文）→ 取签名段作 key 重算 mac → `timingSafeEqual` 比 mac → 查 exp |
| 兼容 | `clientIdentityFromReq` 先试 proof，失败回退整张卡验签。老客户端零影响，**不可一次性删除**旧头 |
| 抓包者能做什么 | 只能在窗口内、冒充**同一个 deviceId** 重放 —— 那个槽位真成员已占，无额外收益。推不出签名段 → 造不出新凭证，也换不了 deviceId |

### 7.1 新增依赖：台账进入验证链路（副作用，必须知道）

验 mac 需要卡的签名段，唯一来源是 `gate_cards.jsonl`。台账因此从「审计记录」变成**验证链路上的必需品**：

- 内存索引 `gateCardIndex`（**`payload 段 → {token, uid}`**）：启动 `loadGateCardIndex()` 全量载入，签发时 `indexGateCard` 同步入表。探活是热路径，不读盘。
- **索引键必须是 payload 段，不能用 jti**。两个原因：① proof 里天然带着完整 payload，命中即证明它就是台账里某张卡的原文（自编 payload 哪怕借了真卡号也必然 miss），不必再单独比对一次；② jti 上线前签发的老卡 payload 里没有 jti，拿 jti 当键会让这些卡**永远查不到** → 持老卡的成员在新客户端下静默变成「无 uid」，严格模式下被永久拒。jti 只用于卡级吊销，**不参与验证**。
- **台账丢失 / 被清 / 手工换过** → 查不到 payload → `verifyGateProof` 返回 null → 该客户端降级为「无签名 TOKEN」（**不硬拒**）。但此时若**严格模式开着，后果是全员被拒**。
- 卡都由本服务签发，故启动载入一次即够；手工编辑台账后需重启更新服务。
- **签发时台账写失败 = 签发失败**（`signGateToken` 检查 `appendGateCard` 返回值）。台账进链路后，写不进去就等于签了一张注定验不过的卡；若照常返回成功，运维会把废卡发给成员，成员永远「无 uid」，严格模式下永远被拒，而没人知道问题出在签发那一刻。宁可当场报错让人修盘/权限。

### 7.2 排障

`verifyGateProof` 失败会打节流日志（同一原因每 60s 一条）：`gate proof reject: <code> <详情>`。

| code | 含义 |
|---|---|
| `mac-mismatch` | 客户端与服务端 HMAC/base64url 口径不一致（跨语言实现差异），或 deviceId 头与算 mac 时用的不是同一个值。详情里的 uid 可信（此时 payload 已与台账逐字节比对过） |
| `ledger-miss` | 台账里查不到这个 payload：台账被清/被换过、**台账行缺 `token` 字段**（早期签发的行），或卡不是本服务签的。详情里的 uid **未经验证**，只作线索 |
| `ts-skew` | 成员机器时钟偏差超窗；详情给出偏了多少秒 |

> 注意「整张卡回退路径」只对**老客户端**成立：回退的输入是 `X-XCat-Gate-Token` 头，而新客户端只发 proof、根本不发这个头。所以「新客户端 + 台账里查不到的卡」= 无 uid，没有第二条路可走，只能重签一张卡。本仓当前台账 9 行里有 1 行（最早那张自用测试卡）缺 `token` 字段，属于这种情况。

**节流键只能是上面那组固定 code，变量一律走「详情」参数**：`/update/access.json` 公网可达且不校验凭证，键里一旦掺入请求可控的值（jti / uid / 偏差秒数），任何人换着值刷就能把节流表撑爆 → 未授权远程内存耗尽。`_gate_proof_test.mjs` 第 13 项用「400 次伪造凭证只许打 ≤2 条日志」把这条钉住。日志里出现的 uid/jti 都先过 `logSafe` 去掉控制字符，防伪造日志行。

> 部署顺序有要求：**先更新服务端，再发客户端包**。新客户端只发 proof，老服务端不认这个头会把它当成无 uid。

服务端拿到的 `gateUid` 贯穿：探活判定（严格模式 / uid 封禁 / 卡级吊销 / 配额）、在线追踪（`activeClients` 每条记 uid）、`/admin/clients` 输出。完整卡与派生凭证都**不进**访问日志、在线表、`client-history.json`（那里只有 uid）。

## 8. 运维台 UI（连接与访问）

| 位置 | 能力 |
|---|---|
| 在线表 TOKEN 列下方 | 绿色 `uid:xxx`（验签得来，不可伪造）；筛选框可按 uid 搜 |
| 每行 禁止/解禁/加白/移出 | 客户端**带 uid 时按 uid 操作**（本人所有设备一起封/解，改硬件无效）；无 uid 自动退回按硬件；tooltip 标明当前走哪种 |
| 「访问策略」行 | **严格模式**勾选框 → `setstrict`；`/admin/clients` 回传 `strictToken` 回显当前态。**开启**弹二次确认，摆出当前在线里没有签名 uid 的台数与后果（写粘性/需再探活才解）；**关闭**即时生效 |
| 台数配额页（mainTab=3） | 按 uid 看在用/上限、改 `max`、释放某设备名额；设备明细按**闲置降序**（僵尸置顶），闲置文案 ≥阈值标红 / ≥1/4 阈值标黄；批量清僵尸带释放前确认（见 6.1）。新增框台数**默认预填 100**，空态 hint 写「不限」——留空或填 0 才是不限；保存后恢复 100 而非清空（清空的语义是不限，留在框里会让下一次操作误设成不限） |
| 签卡页（mainTab=4） | 签发（uid + 天数 + 台数上限 + 备注）；填 uid 即回显**他名下最新卡的状态**（有效/过期/已吊销）与**台数已用**，避免重复签发或把上限设成他早已超掉的数。台数**默认 100**，三态：填数字=设成该值 / **留空=不动他现有上限**（空态 hint 写「不改」）/ 填 0=明确设成不限 |

> 两个入口的「留空」语义**故意不同**，不是疏漏：配额页留空=不限（那是设值入口）；签卡页留空=不动现有上限（那是签卡入口，给老成员重签时忘填不该把他已设好的上限静默抹成不限）。默认值定 100 而不是 0 的理由见 6.2。
| 签卡页 · 签发台账 | 服务端按签发倒序返回；同 uid 的历史卡默认**折叠**（状态列「已被取代」，一键复制 TOKEN 禁用），勾「显示历史卡」才全列 |
| 签卡页 · 台账「这张卡」列 | **废卡 / 恢复卡** → `revokeJti` / `unrevokeJti`（只动这一张）；无卡号的老台账行显示「无卡号」并说明为何废不掉 |
| 签卡页 · 台账「整个人」列 | **封人 / 解禁** → 按 uid 封（名下所有卡一起拦）。状态列用「卡已废」/「人已封」区分两种粒度 |

## 11. 安全边界（别高估）

| 层 | 强度 | 说明 |
|---|---|---|
| gate/1 本地验签 | 中 | 拦「拿到就跑」的外人；exe 可被逆向 patch 跳过——不追求不可破，靠在线门补 |
| uid 封禁 | **高** | uid 由服务端验签，客户端改不了；封了就拦，改硬件/换 MAC/清目录都无效 |
| 卡级吊销（jti） | **高** | jti 同样出自验签 payload，客户端改不了；粒度到单张卡，但**只在联网探活时生效** |
| 严格模式 | 高 | 开启后无签名 TOKEN 直接拒，堵住「本地绕过 gate/1 后还想连服」的口子 |
| deviceId 台数 | 低-中 | 随机 UUID 可伪造，配额数量可能被灌水；要精准需升级软件指纹 |

**结论**：不可伪造的锚是 **uid**（封人 + 记账都以它为准）与 **jti**（废单张卡）；本地 gate/1 是第一层劝退，严格模式 + uid/jti 吊销是真正的止血闸。

> ⚠️ **吊销靠联网生效，延迟上界 = 租约 TTL（64h）**。gate/1 是纯本地验签，服务关着时一张已废的卡照样能进主界面；且 `EnforceOnlineLeaseGateOnStartup` 在租约有效期内**不做前台探活**（`OnlineLeaseValid` 为真即放行），所以废卡不会立刻拦住已有租约的人。
>
> 但对方要想继续启动，**必须每 64h 成功探活一次**（租约过期后不探活成功就起不来，且 1h 宽限是整机一次性的），而成功探活必然撞上吊销判定 → 当场 Denied + 写粘性 + `ClearOnlineLease`。故只要服务端在这 64h 窗口里有开过，吊销一定落地；对方若在开服时段挂着 XCAT，周期探活（约 60s）会当场把他踢掉。
>
> 反过来这条也是**正常成员的误拦风险**：每 64h 必须撞上一次开服窗口，否则租约过期 → 启动被 gate/3 硬拒（宽限早已用掉），症状是「莫名启动不了」。开服时段固定且与部分成员作息持续错开时会踩到。**运维台「历史客户端 · 租约预警」就是为提前看见这批人而做的**（见第 12 节）。

## 12. 客户端历史台账（跨重启可追溯 + 租约预警）

**病根**：`activeClients` 是内存 Map，`kClientPruneSec` 到点就删（默认 1h），进程重启即清空。于是运维台只看得到「此刻在线」——而**掉租约的人恰恰是那批没在线的**，永远看不见，只能等成员报「用不了」。

`scripts/twms-client-history.mjs`（刻意与 `activeClients` 分开，不动在线判定口径）：

| 项 | 约定 |
|---|---|
| 分工 | `activeClients` 管在线表 / geo / 同 IP 告警（内存、短窗口）；本模块只管可追溯字段（落盘、按天老化） |
| 落盘 | `artifacts/release/client-history.json`，`version:1`，tmp + rename 原子写 |
| 写入时机 | `touchClient` 末尾、`noteAccessAllow`、`noteAccessDeny` 各 `touch(row)` 一次 |
| 节流 | 脏标记 + 最小写间隔 20s（探活约 60s/客户端，不能每请求落盘）；定时器 `unref` 不吊住进程；`/admin/shutdown` 与 SIGINT/SIGTERM 前 `flush()` |
| 老化 | 默认保留 30 天（`XCAT_TWMS_CLIENT_HISTORY_DAYS` 可调），`load` 与新增记录时各 prune 一次 |
| 字段口径 | 只写有值的字段，空值**不抹**旧快照（未进图的探活不该把角色名清空）；`lastAllowAtMs` 是租约估算的锚 |
| 租约剩余 | `lastAllowAtMs + 64h - now`，与 `gateViewForRow` **同口径** |
| 端点 | `GET /twms/admin/client-history?days=&limit=`；`online` 字段由内存 `activeClients` 交叉标注 |

运维台「连接与访问」页下方折叠区「**历史客户端 · 租约预警 N**」：默认只列**离线且租约剩余 <12h** 的（标题上的 N 就是这个数，有则默认展开），可切「全部」、可改天数窗口。租约剩余按在线/告警/过期三色，「最后拒绝」列直接显示 `match + reason`（如 `jti card revoked`），事后查「他为什么用不了」不必翻日志。

> 台账含成员 uid / IP / 机名 / 角色名，已在 `.gitignore` 显式排除（连同 `device-access.json`、`device-quota.json`）。
